# Libre AI Execution Sandbox

## Intended use

Provide an execution boundary that constrains a worker according to an explicit admitted profile and records the outcome actually observed. Missions describes requested work and Mission Control coordinates it; neither replaces the operating-system controls that confinement requires.

## Existing candidates and limits

Earlier Harness sources and separate bounded local qualification candidates exist. Their exact platform and revision limits must be preserved; neither an old README nor a successful isolated campaign admits all execution profiles or the final distributed tool. This documentary candidate admits no generally available sandbox or universal confinement guarantee.

## Proposed contracts

An execution request specifies the intended profile and the authority for its allowed effects. A result distinguishes a pre-launch refusal, successful completion, interruption and unavailable evidence. Missing prerequisites must produce a refusal rather than weaker execution. An attestation reports observations within its qualified scope; it is not permission to perform an action.

## Activation criteria

Qualify the exact platform, toolchain and profile with independent success, refusal and confinement tests and the reviewed per-file coverage controls. The chosen Linux behavior cuts off a worker when its channel closes; this may refuse a normal program and must remain documented and tested. Verify cleanup and integration with the actual consumer without assuming that an authorization decision supplies confinement.

Qualification follows the actual selected scope. A candidate module may be admitted independently with its own consumer and evidence; complete journey criteria apply to the corresponding product or integration. A pure core does not require a worker, database or relay integration that is outside its scope. Neither module admission nor this repository’s documentary existence requires a complete Missions journey.
